# AGENTS.md

Guidance for AI coding agents working in this repository. See `README.md` for user-facing docs.

## What this is

A single-product Stripe storefront (Bluebird House, $40). Pages (`/` hero, `/login`, `/products` listing, `/products/:slug` detail, `/cart`, `/checkout`, `/checkout/pay`, `/order`, `/admin/*`) are server-rendered by PureScript (`src/Html.purs`, `src/Server/*.purs`, bundled to `server/views.js`) with HTMX; the only client code is `src/Client/*` (Stripe Elements and Umami), bundled by Vite. An Express 5 server (`server/index.js`) serves both. Deployed as a unikernel on Datum Cloud with `run.hs`.

## Commands

- `npm install`, then `npm run dev` for local development (compiles PureScript, runs Vite and the API).
- `npm run build` must pass with no PureScript warnings before you finish. `npm start` serves `dist/` plus the API on one port.
- There is no test suite. Verify UI changes by running the built server and loading the page; use Stripe test-mode PaymentIntents (card `pm_card_visa`, declined `pm_card_chargeDeclined`) for the confirmation page.
- Deploy: `./run.hs --project <project> --pull-secret <secret>`. This replaces the running production instances (two, rolled one at a time), so ask first. `.github/workflows/deploy.yml` runs the same script: every push to `main` deploys dev as `vX.Y.Z-dev.N`, and publishing a `vX.Y.Z` GitHub release deploys that tag to prod. It signs in with the `DATUM_CREDENTIALS` service account secret and pushes with `GITHUB_TOKEN` (`run.hs --registry-user`). The version comes from git tags (README "Versions and releases"); `run.hs` waits until `/api/health` reports it with `migrations: ok`, so keep both fields honest.
- AWS account setup and migration: `./ops/aws-account.hs setup|copy-data|switch|destroy`. Run it with an admin profile for the target account; `switch` restarts Postgres and `destroy` deletes data, so ask first. DNS changes still need approval.
- Auth deploy: `./auth/deploy.hs --project <project> --admin-email <email>`; the store's OIDC secret is created by `./scripts/store-auth-secret.hs --project <project>`. The full watcher deploy and AWS setup need IAM (`drewr-root`); `./ops/watch/deploy.hs code` is enough for `checks.json`/Lambda changes.

## Conventions

- Every script is a self-contained Haskell (turtle) script with a `nix-shell` shebang, like `run.hs`: executable, with its tools named in the shebang and run from the repository root. Do not add bash or node scripts. The one exception is a script that runs inside a container image (for example the Postgres entrypoint), where Nix is not available.

- The server sets prices. Never accept an amount from the browser; the unit price lives only in `server/price.js`, the delivery fee only in `delivery_settings`, and checkout takes the quantity and delivery choice from the signed cart cookie (`server/cart.js`) and re-validates both.
- Delivery is local pick-up at slots admins define on `/admin/pickup` (docs/design/fulfillment.md), plus local delivery when an admin switches it on at `/admin/delivery` (docs/design/local-delivery.md). Shipping is shown greyed out until USPS pricing is added; there is no USPS code yet.
- Local delivery is a flat per-order fee within a radius of a home base. The radius is checked on the exact street address with the US Census Geocoder (no key) by `/api/delivery/verify`, which then sets the verified address on the PaymentIntent; if Census is down or can't match the street it falls back to the ZIP centroid and the order's `address_check` says so. Wallet sheets (Express Checkout) reveal only the ZIP until confirm, so `/api/delivery/check-zip` uses centroids. The centroids are `server/data/zcta-centroids.json`, generated by `scripts/zcta-centroids.hs` from the Census Gazetteer; rerun it when a new year is published.
- Store admins are members of the Rauthy group `birdhaus-admins` (`run.hs --admin-group`), not Rauthy admins. The store requests the `groups` scope, so each store client in Rauthy must list `groups` in its Allowed Scopes. The admin flag is re-read at sign-in and lapses after 12 hours; `/admin` stays `no-store` and its POSTs must be same-origin.
- `/api/order/:id` must keep requiring the matching `client_secret` and `Cache-Control: no-store`; it returns buyer PII.
- The secret key is server-side only. Never expose it through a `VITE_` variable or the client bundle.
- Keep pages `no-cache` (`/order` and `/admin` `no-store`) and hashed `/assets` immutable; the server links the hashed client bundle from Vite's manifest.
- Add PureScript dependencies in `spago.yaml`; `spago.lock` is generated and committed.
- Match the existing style: terse comments that explain why, no dead code.
- Products are listed in `server/products.js` (slug, name, summary, image, visibility, batched); prices stay in `server/price.js`, keyed by slug, and availability comes from the batch for batched products. `visibility` is `"public"` or `{ groups }` (Rauthy groups, kept in the session and lapsing with the admin flag); a hidden product is left out of the listing, redirects from its page, and can't be added to or kept in the cart. The cart holds one product at a time. Demo Thing ($0.50, admins only, unbatched) exists to test checkout with a real card. The homepage hero image is in `homePage` (`src/Server/Render.purs`); its text, like any section listed in `server/copy.js`, is edited by admins at `/admin/site` and stored in `site_copy`, with the built-in text as the fallback (docs/design/site-copy.md). Admin text is rendered as Markdown with HTML allowed and always sanitized before it reaches a page.
- Styles live in `src/styles/` (docs/design/styles.md): `index.css` sets the cascade-layer order (reset, tokens, base, layout, components, pages) and imports one file per component or page into its layer. Use Open Props' scales for every size, never a literal: `--size-1…15` for spacing, `--size-content-*`/`--size-header-*`/`--size-xxs…xxl` for widths, `--size-fluid-*`/`--font-size-fluid-*` where it should scale with the window, `--font-size-0…8` (text is 12px `--font-size-0` or 16px `--font-size-1`, not in between), `--border-size-*`, `--ratio-*`, and breakpoints as `@media (--md-n-below)`/`(--sm-n-below)` (postcss-custom-media). Brand colours and fonts are ours, in `tokens.css`. `postcss-jit-props` (`vite.config.js`) emits only the props used. Page titles share `page-title`, and Stripe Elements get the tokens through `stripeAppearance()` in `src/Client/Main.js`. A rule whose class no view emits is dead: delete it.

- Brand images in `public/` are generated from `brand/` by `scripts/brand-assets.hs`; edit the script or sources, not the outputs.

- Product photos are listed per product in `server/products.js` (name and alt text, first is the default) and generated by `scripts/product-photos.hs <slug> name=path…` from the owner's originals, which are not committed: square WebP at 160/480/800/1200px with all metadata stripped, into `public/photos/<slug>/` with content-hashed names (served immutable from `/photos`) and listed in `server/data/photos/<slug>.json`. The server refuses to start if a listed photo has no files.

- DNS records we write by hand live in `dns/` and are the source of truth; apply them with `datumctl apply -f dns/ --project <project>`. `dns/ses.yaml` is generated by `ops/aws-account.hs setup`, not edited by hand.

- Operator alerts: `ops/watch/` (birdhaus-watch in AWS) emails on failures. Keep `/api/health` honest and cheap, and keep the Postgres watchdog in `postgres/entrypoint.sh` reporting every 5 minutes; a new component that can fail silently should get a check in `ops/watch/checks.json`.
- Design docs live in `docs/design/`. Postgres on S3 is built and deployed as workload `birdhaus-pg` (deployment `birdhaus-db`) in the `birdhaus` Network (`network/`), with the store, Umami (`umami/`, https://stats.birdhaus.store) and Rauthy (`auth/`, https://login.birdhaus.store) as consumers through `db.birdhaus.store` (`dns/aaaa.yaml`). `datumctl compute build` makes unikernel images only, so general-purpose workloads are built with nerdctl.

## Secrets and safety

- `.env` holds Stripe **test** keys. `.env.production` holds **live** keys. Do not read, copy, or create cloud secrets from live keys unless the user explicitly says so.
- Only `.env.example` is tracked (see `.gitignore`). `workload.yaml` is written by `datumctl compute deploy`; `run.hs` is the source of truth.
- Keep personal details (emails, session names) out of committed files; pass them as `run.hs` arguments.
- Tests that create Stripe objects must refuse non-`sk_test_` keys.

## Deployment facts

- Image: `ghcr.io/<gh user>/birdhaus-store`, private; the workload pulls it with an `imagePullSecrets` entry.
- Workload `birdhaus-store` runs in `us-east-1` on the unikernel runtime and listens on 8080. `run.hs` also applies a NetworkService and HTTPProxy for the domain `birdhaus.store`.
- The `datumctl compute deploy -f` flag cannot be combined with `--http-port`, which is why networking is applied separately.
- Store builds use `datumctl compute build` with the container engine's BuildKit; `BUILDKIT_HOST` overrides it. The Postgres image builds with colima/nerdctl.
- Orders are recorded only from the signature-verified Stripe webhook (`/api/stripe-webhook`), never from the browser return page. The webhook must stay idempotent (PaymentIntent ID as key) and return 500 on database errors so Stripe retries.
- The store must keep selling when Postgres is down (to signed-in customers): database calls fail open for checkout and are retried by Stripe for records. Schema changes are new numbered files in `server/migrations/`; never edit an applied one.
- Accounts: Rauthy (`auth/`) is the identity service at https://login.birdhaus.store, but customers never use its pages (docs/design/login-page.md). The store's `/login` offers Google (through Rauthy with `idp_hint`, resolved by provider name, so nothing is chosen there) and passwordless email: the store emails a 6-digit code (`server/email-login.js`, `login_codes`, SES SMTP from `birdhaus-ses`) and manages the account through Rauthy's admin API with an API key (`server/rauthy.js`, the `birdhaus-store-rauthy` Secret from `scripts/store-rauthy-key.hs`). Never link customers to Rauthy's own pages; sign-out only visits Rauthy when the Google ID token can be passed silently. Checkout (`/checkout*`, `/api/create-payment-intent`, `/api/delivery/*`) and the waitlist require an account (`requireAccount`); browsing and the cart don't. The store's `birdhaus-store-auth` Secret points server-side OIDC and the admin API at `http://auth-internal.birdhaus.store:8080`, whose AAAA in `dns/aaaa.yaml` must be updated when `birdhaus-auth` is replaced. Orders link by `orders.account_sub`. Auth mail uses SES SMTP (`birdhaus-ses`), not Mailgun. The auth `TRUSTED_PROXIES` value is still permissive and needs narrowing.
